# elb: 2 net-new causes — no Classic ELB data-plane scenario reaches a verdict (a registered instance never becomes InService and no request is ever forwarded), and the DeleteLoadBalancerPolicy in-use refusal message is emulator-authored

> _Note: this issue was identified against the code base at commit `2bac9c0c7897d6c2f9107b98647560d403e99572`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInstanceHealth

## Description
2 net-new causes, both in the ELB Classic (elasticloadbalancing) emulator. None of the failing checks below is marked ALREADY FILED or OWNED in the replay report, so none is gated by an existing issue; the open issues that report the same faults from other recorded units are named per cause.

Cause 1 of 2 — a Classic load balancer never has a registered instance in service and never forwards a request, so every Classic data-plane scenario burns its whole budget without reaching an assertion. Failing checks: elb.instance-health-decides-whether-real-http-reaches-the-backend, elb.out-of-service-instance-blocked-from-receiving-traffic, elb.registered-instance-serves-real-http-through-elb-dns-name, elb.lb-cookie-stickiness-pins-a-client-to-one-registered-instance, elb.lb-cookie-stickiness-pins-client-to-one-instance.
AWS: Smithy: DescribeInstanceHealth input {LoadBalancerName required, Instances}, output DescribeEndPointStateOutput {InstanceStates: InstanceState {InstanceId, State 'InService|OutOfService|Unknown', ReasonCode 'ELB|Instance|N/A', Description}}; errors LoadBalancerNotFound (400) and InvalidInstance (400). State is the OUTCOME of the load balancer probing each registered instance on the target ConfigureHealthCheck stored: after HealthyThreshold consecutive successful probes of Target (here 'HTTP:80/ping' or 'HTTP:80/ok', Interval 5, Timeout 2, thresholds 2) the member reads State='InService', ReasonCode='N/A', Description='N/A' — those three strings are AWS's fixed text, only InstanceId comes from the request. An instance that is InService then RECEIVES traffic: an unsigned HTTP GET of the load balancer's published address is forwarded to it and the client gets the backend's own bytes and status (including a 404 the backend itself chose), an instance that falls below the threshold is taken OutOfService and stops receiving requests while a healthy sibling keeps serving, and with a duration-based policy attached by CreateLBCookieStickinessPolicy + SetLoadBalancerPoliciesOfListener the listener mints Set-Cookie: AWSELB=<opaque> and pins every request carrying it to the one instance that served it while a cookie-less client is still spread.
Emulator: all five checks end with 'Check timed out after 60.0s' and produce no assertion value at all — each is still inside its bounded poll (DescribeInstanceHealth for State='InService', or the bounded 200-body poll through the load balancer) when the wrapper ends it. By construction neither poll can ever be satisfied: the data plane's own documentation in the crate states that no instance of this emulator runs a server on a port, so the connection to the selected instance cannot be established and the plane answers only its no-instance / instance-unreachable statuses, and the same unreachable backend makes every health probe fail, so a registered instance never reaches InService. Hypothesis: with health stuck below InService the stickiness legs (AWSELB cookie minting and pinning) are never reached, so whether stickiness is implemented is not observable from these checks.
Why: a client cannot tell a healthy backend from a failed one, and every deploy/registration gate that waits for InService before sending traffic blocks until its own timeout. Nothing behind that gate is reachable either: no request is ever served through a Classic load balancer, so listener forwarding, the withdrawal of an unhealthy instance, the 503/504 statuses and the AWSELB stickiness contract are all unobservable. A Classic load balancer that never has an InService instance never serves traffic at all.
Fix: the health-check evaluation feeding the per-load-balancer instance-health state read by the DescribeInstanceHealth handler, and the data plane's connection to a selected instance — a registered instance must be able to pass its probes and emit the InService / 'N/A' / 'N/A' triple, and a request to the load balancer must reach the backend the instance id names so the backend's own status and body are returned. That requires the EC2 side of the emulator to let a launched instance serve on a port (its user data is currently interpreted as a shell session with no network), which is the platform half of this cause.

Code: services/service-com-amazonaws-elasticloadbalancing-elasticloadbalancing-v7/src/service/data_plane.rs (eligible_instances, NO_IN_SERVICE_INSTANCE_STATUS, INSTANCE_UNREACHABLE_STATUS), src/service/stickiness.rs, src/state.rs (instance_health / settle_instance_health), src/ops/describe_instance_health.rs; services/service-com-amazonaws-ec2-amazonec2/src/state/guest_console.rs. Cause 2 of 2 — DeleteLoadBalancerPolicy refuses a policy a listener still references with the right code but emulator-authored message text. Failing check: elb.stickiness-policy-deletion-while-attached-to-listener-rejected.
AWS: Smithy: DeleteLoadBalancerPolicy input {LoadBalancerName required, PolicyName required}, errors LoadBalancerNotFound (400) and InvalidConfigurationRequest (awsQueryError httpResponseCode 409). Deleting a policy while a listener still references it (SetLoadBalancerPoliciesOfListener having enabled it) is refused with code InvalidConfigurationRequest and the message 'You cannot delete policy [<PolicyName>] since it is enabled or referred by other enabled policy.' — every word of that sentence, including the square brackets, is AWS's fixed text; the only variable part is <PolicyName>, taken from the request. Recorded behavior confirms that wording.
Emulator: the code is correct (InvalidConfigurationRequest) but the message is re-worded as 'Policy [<PolicyName>] cannot be deleted because it is enabled for the listener on port <port>' — the replay observed 'Policy [sim2real-sticky-3fa9fa29780a] cannot be deleted because it is enabled for the listener on port 80', where the policy name is the request's value and 80 is the listener port from state; the sentence itself is the emulator's own text, and it names a listener port AWS's message does not mention at all.
Why: a client that matches on the message — a test asserting the documented sentence, a log scraper, an operator runbook, an SDK wrapper that surfaces the message to a user — sees text AWS never produces, so a correctly refused delete reads as an unknown failure. The message is part of the error contract, not a cosmetic detail.
Fix: the message construction in the DeleteLoadBalancerPolicy handler's in-use validation — it must emit AWS's fixed sentence with the requested PolicyName interpolated and no listener port.
Traces: check elb.stickiness-policy-deletion-while-attached-to-listener-rejected. Code: services/service-com-amazonaws-elasticloadbalancing-elasticloadbalancing-v7/src/ops/delete_load_balancer_policy.rs, src/ops/set_load_balancer_policies_of_listener.rs.
