# ElastiCache transient lifecycle windows are not observable: creating/modifying/deleting settle before a client's first read, so five state-gated behaviors diverge (5 causes)

> _Note: this issue was identified against the code base at commit `22429b7a0c0ae7d0c87a7901239a937fd78a2091`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RebootCacheCluster

## Description
Five net-new root causes in the elasticache emulator, grounded in five failing behavioral checks the suite marked neither ALREADY FILED nor OWNED. They share a mechanism (see the note after Cause 5), but each is a distinct observable behavior with its own operation, its own refusal code and its own message, so each must be closed and re-replayed on its own.

Cause 1 of 5: a cache cluster is never observable in status 'creating', so RebootCacheCluster and CreateSnapshot never apply their creating-state gate.
  AWS: Smithy (services/service-com-amazonaws-elasticache-amazonelasticachev9) models RebootCacheCluster with InvalidCacheClusterStateFault (awsQueryError code InvalidCacheClusterState, HTTP 400) and CacheClusterNotFoundFault (CacheClusterNotFound, 404); CreateSnapshot models the same InvalidCacheClusterStateFault. Recorded behavior: after CreateCacheCluster(Engine=redis, NumCacheNodes=1) the cluster holds CacheClusterStatus 'creating' for minutes, and a DescribeCacheClusters issued straight after the create reports 'creating'. RebootCacheCluster in that window is refused 400 InvalidCacheClusterState with the message 'Can only reboot cache clusters with state in: available, incompatible-parameters, snapshotting. Cluster <CacheClusterId> has state: <status>.' — fixed text 'Can only reboot cache clusters with state in: available, incompatible-parameters, snapshotting. Cluster ' + ' has state: ' + '.', the two variable parts being the CacheClusterId from the request and the cluster's current status from the store (here 'creating'). CreateSnapshot in that window is refused 400 InvalidCacheClusterState with the wholly fixed message 'Cluster must be in available state in order to create a snapshot.' Once available the same reboot succeeds, and after the cluster is deleted the reboot answers 404 CacheClusterNotFound 'CacheCluster not found: <CacheClusterId>'.
  Emulator: the DescribeCacheClusters issued immediately after CreateCacheCluster already reports CacheClusterStatus 'available' (replay detail: 'AssertionError: cluster became available before reboot could be attempted while creating'), so neither state gate is ever reached and the check cannot observe the refusal, its code or its message.
  Why: a client that guards a reboot or a snapshot on InvalidCacheClusterState (retry-until-available loops, SDK waiters, CloudFormation-style provisioning) sees a cluster that is 'available' the instant it is created and a reboot/snapshot accepted where AWS refuses it. Code paths written for AWS's provisioning window are never exercised, and the opposite bug — a client that reboots a half-built cluster — is silently rewarded here and fails against AWS.
  Fix: the cache-cluster state in the elasticache crate — the transition span and the settling path that reads it, so a cluster the create put in 'creating' is still reported 'creating' to a client's immediate read for a span comparable to AWS's, with the RebootCacheCluster and CreateSnapshot handlers' state gates refusing inside it.
  Traces: elasticache.reboot-cache-cluster-invalid-state.

Cause 2 of 5: ModifyCacheCluster(ApplyImmediately=true) leaves no observable 'modifying' window, so RebootCacheCluster's modifying-state gate is never reached and the check burns its whole budget polling for it.
  AWS: Smithy models ModifyCacheCluster with InvalidCacheClusterStateFault (InvalidCacheClusterState, 400) and RebootCacheCluster likewise. Recorded behavior: ModifyCacheCluster(CacheClusterId, NumCacheNodes=2, ApplyImmediately=true) on an available memcached cluster answers CacheCluster.CacheClusterStatus 'modifying' (or briefly 'available'), DescribeCacheClusters then reports 'modifying' while the scale-out runs, a RebootCacheCluster in that window is refused 400 InvalidCacheClusterState with 'Can only reboot cache clusters with state in: available, incompatible-parameters, snapshotting. Cluster <CacheClusterId> has state: modifying.' (same fixed text as Cause 1; the variable parts are the request's CacheClusterId and the store's current status), the refused reboot leaves the status 'modifying', and the cluster later settles 'available' with NumCacheNodes 2.
  Emulator: the check dies with 'Error: Check timed out after 60.0s' inside the poll that waits for CacheClusterStatus to become 'modifying' (interval 3 s, bound 180 s) — no assertion fires, so the emulator never reported 'modifying' to any read. Hypothesis for the mechanism: the modify's transient status falls due before the client's first poll can see it (see the shared-mechanism note below), so the cluster reads 'available' continuously and the wait can never be satisfied.
  Why: a client that applies a change with ApplyImmediately and then polls for 'modifying' -> 'available' (the documented sequence) never sees the change begin; the wait never converges and the client cannot distinguish 'applied' from 'never started'. A client guarding a reboot on InvalidCacheClusterState also gets a reboot accepted mid-modification, which AWS refuses.
  Fix: the ModifyCacheCluster handler and the cache-cluster state transition it writes — keep the cluster in 'modifying' for a span a client's read observes, and make RebootCacheCluster refuse inside it with the message above.
  Traces: elasticache.cache-cluster-reboot-rejected-during-pending-modification.

Cause 3 of 5: a replication group is never observable in status 'creating', so DeleteReplicationGroup never applies its creating-state gate.
  AWS: Smithy models DeleteReplicationGroup with InvalidReplicationGroupStateFault (awsQueryError code InvalidReplicationGroupState, HTTP 400) and ReplicationGroupNotFoundFault (404). Recorded behavior: after CreateReplicationGroup(Engine=redis, NumCacheClusters=1, AutomaticFailoverEnabled=false) a DescribeReplicationGroups issued straight after the create reports Status 'creating' and holds it for minutes; DeleteReplicationGroup in that window is refused 400 InvalidReplicationGroupState with 'Cache cluster <member-cluster-id> is not in a valid state to be deleted.' — fixed text 'Cache cluster ' + ' is not in a valid state to be deleted.', the variable part being the group's first member cluster id, which AWS ids as <ReplicationGroupId>-001 — and the group still reads 'creating' afterwards. Once available the delete is accepted, answers the group's id, its Description and Status 'deleting', and the id then reads 404 ReplicationGroupNotFoundFault 'ReplicationGroup <id> not found.'
  Emulator: the first DescribeReplicationGroups after the create already reports Status 'available' (replay detail: "AssertionError: expected the group to still be creating, got 'available'"), so the state gate is unreachable and the refusal, its code and its message are never produced.
  Why: a client that creates a replication group and then waits for it, or that guards teardown on InvalidReplicationGroupState, is told a multi-node group is usable the instant the create returns; a delete issued against a half-built group is accepted where AWS refuses it, and the AWS-shaped retry loop is never exercised.
  Fix: the replication-group state in the elasticache crate (its transition span and settling path) plus the DeleteReplicationGroup handler's state gate. Note the open issue 20261109T193317Z-elasticache-deletereplicationgroup-answers-notimplemented-instead-of-its-two.md covers DeleteReplicationGroup's snapshot-in-progress and migration gates; it does not carry this check id or the creating-window refusal above.
  Traces: elasticache.delete-replication-group-wrong-state-rejected.

Cause 4 of 5: CreateUserGroup answers Status 'creating' but the very next DescribeUserGroups reports 'active', so DeleteUserGroup never applies its creating-state gate.
  AWS: Smithy models DeleteUserGroup with InvalidUserGroupStateFault (awsQueryError code InvalidUserGroupState, HTTP 400) and UserGroupNotFoundFault (UserGroupNotFound, 404). Recorded behavior: CreateUserGroup(Engine=redis, UserIds=['default']) answers Status 'creating' and DescribeUserGroups keeps reporting 'creating' until the group settles; DeleteUserGroup inside that window is refused 400 InvalidUserGroupState with 'User group <UserGroupId> has status creating. Only active or create-failed user groups can be deleted.' — fixed text 'User group ' + ' has status ' + '. Only active or create-failed user groups can be deleted.', the variable parts being the UserGroupId from the request and the group's current status from the store — and the refused delete leaves the group to settle 'active'.
  Emulator: the create response does report 'creating', but the DescribeUserGroups issued immediately after it reads 'active' on every attempt, across five freshly created groups (replay detail: "AssertionError: DeleteUserGroup was never refused while creating in 5 groups: [\"<id>: read 'active' before the delete\", ...]" — the ids are per-run values, the pattern is that every first read is already 'active'). The refusal is therefore never produced.
  Why: a client that creates an RBAC user group and polls it, or that handles InvalidUserGroupState while tearing one down, sees a group that is active before it exists and a delete accepted during creation; the state the create response advertises is contradicted by the next read, which is itself a divergence a client cannot work around.
  Fix: the user-group state in the elasticache crate — hold the group in 'creating' for a span DescribeUserGroups reports, and make the DeleteUserGroup handler refuse inside it with the message above.
  Traces: elasticache.user-group-delete-while-creating-rejected.

Cause 5 of 5: after DeleteServerlessCache the cache is already gone to the next read instead of being reported Status 'deleting'.
  AWS: Smithy models DeleteServerlessCache -> DeleteServerlessCacheResponse$ServerlessCache and errors InvalidServerlessCacheStateFault (400) and ServerlessCacheNotFoundFault (404); ServerlessCache$Status is documented 'CREATING, AVAILABLE, DELETING, CREATE-FAILED and MODIFYING' and the recorded wire values are lower case. Recorded behavior: DeleteServerlessCache answers the cache with Status 'deleting', a DescribeServerlessCaches issued immediately after the delete still returns that cache with Status 'deleting', and only later does the name read 404 ServerlessCacheNotFoundFault 'Serverless cache with name <name> not found.' (fixed text 'Serverless cache with name ' + ' not found.', the variable part being the requested ServerlessCacheName), with ModifyServerlessCache on the dead name failing the same way.
  Emulator: the DescribeServerlessCaches issued immediately after DeleteServerlessCache returns no such cache — the check's describe wrapper maps the 404/empty list to None and the assertion on Status 'deleting' fails with 'AssertionError: None'. The handler does write the DELETING status and a pending removal (services/service-com-amazonaws-elasticache-amazonelasticachev9/src/ops/delete_serverless_cache.rs:273-283, begin_deletion), but the read path carries the pending removal through before answering, so the deleting window is never visible.
  Why: a client that deletes a serverless cache and then polls DescribeServerlessCaches for Status 'deleting' -> gone (the AWS-documented sequence, and what SDK waiters do) sees the resource vanish in one step; a 404 on the first poll is indistinguishable from 'the delete never took effect for this name', and any code that reads the deleting record (to log its ARN, to confirm a FinalSnapshotName was taken) gets nothing.
  Fix: the serverless-cache read path in the elasticache crate's state (the settled/awaiting read helper DescribeServerlessCaches and DeleteServerlessCache share) — report the record in 'deleting' for a span a client's read observes before removing it.
  Traces: elasticache.serverless-cache-lifecycle.

Shared mechanism (not a sixth cause): services/service-com-amazonaws-elasticache-amazonelasticachev9/src/state.rs:414-427 declares CLUSTER_TRANSITION = 500 ms with the contract that 'a REPORT issued inside the span is answered once the transition has fallen due (await_settled), so a client polling on an AWS-sized interval converges on its first poll', and state.rs:429-437 says the same for SNAPSHOT_TRANSITION; the serverless path uses the equivalent settled_serverless_cache_mut. The consequence is that no client read can ever observe a transient status: reads wait the span out and answer the settled value (or, for a delete, the record's absence). Open issue 20261110T144301Z-elasticache-multi-step-lifecycle-flows-never-converge-every.md argues the OPPOSITE direction of the same knob (polls missing and sleeping a full interval) and carries none of the five check ids above; the five behaviors here need the transient status to be observable AND the state gates that go with it to refuse inside it.
