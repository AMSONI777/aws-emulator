# appsync__dynamodb__events: a VTL-resolver-backed putItem mutation never resolves, so both EventBridge→AppSync routing checks exhaust the run budget with no delivery ever observable

> _Note: this issue was identified against the code base at commit `41629e50f0504ce89b4649b5e84534dabeb050dd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PostGraphQL (AppSync GraphQL data plane) / CreateResolver

## Description
Cause 1 of 1: a UNIT resolver on an AMAZON_DYNAMODB data source that is defined by VTL request/response mapping templates never resolves its field, so every check that must first drive `Mutation.putItem` directly (the warm-up that proves the data-source role has propagated) never gets a successful mutation and the check runs out its budget without ever reaching the EventBridge leg it is about. Failing checks: appsync__dynamodb__events.xsvc-appsync-2-near-miss-events-not-delivered-while-the-pipeline-is-live, appsync__dynamodb__events.xsvc-appsync-2-rule-input-transformer-mutation-writes-the-mapped-item.

AWS: mapping templates are a first-class way to define a resolver. Smithy (appsync): Resolver$requestMappingTemplate and Resolver$responseMappingTemplate target MappingTemplate (@length min 1 max 65536, @pattern "^.*$"); Resolver$code (APPSYNC_JS) is documented as the ALTERNATIVE, never a precondition. A UNIT resolver (Resolver$kind UNIT — "run a GraphQL query against a single data source") on a DataSource of type AMAZON_DYNAMODB with dynamodbConfig evaluates the VTL request template (including $util.dynamodb.toDynamoDBJson and the "version": "2018-05-29" PutItem/GetItem operations), performs the DynamoDB call under the data source's serviceRoleArn, and renders the result through the response template. A successful signed mutation is HTTP 200 with data.putItem populated from the written item and NO "errors" member, and the item is readable from the table with ConsistentRead. Consequently an EventBridge rule whose AppSync target names the endpoint ARN and carries AppSyncParameters.GraphQLOperation plus an InputTransformer writes the mapped item, and a near-miss event (detail.kind or detail-type differing only in case) writes nothing and is not even attempted (no DLQ message).

Emulator: the warm-up mutation never resolves. Both checks therefore never leave their first bounded wait ("a signed putItem mutation to resolve (data-source role propagation)", a 150 s budget) and the harness ends them with the only diagnosis it has: "Check timed out after 60.0s". No item is ever written to the DynamoDB table, so neither the positive EventBridge→AppSync delivery nor the near-miss absence can be observed at all. Hypothesis: the same emulator-authored resolver error already filed for the sibling checks of this service — HTTP 200 with data.<field> null and errors[0].message "This field's resolver is defined by mapping templates, which this endpoint does not run; define it with APPSYNC_JS code." (that whole sentence is fixed emulator text; AWS has no such error) — is what these two also hit; the open issue 20261114T043034Z-appsync-dynamodb-events-vtl-mapping-template-resolvers-are.md describes that cause and explicitly states it does NOT claim these two checks, so they are filed here and remain unclaimed otherwise. These two checks additionally cover behaviour that issue does not: case-sensitive rule-pattern near-miss suppression (no write, no DLQ attempt) and InputTransformer-mapped mutation arguments.

Why: a client that defines its AppSync resolvers the documented VTL way gets a field that never resolves and a mutation whose side effect never happens, so nothing downstream of it exists: an EventBridge rule targeting that mutation can neither be shown to deliver a matching event nor to withhold a near-miss one, and dead-letter/no-attempt accounting for an AppSync target is unobservable.

Fix: the AppSync GraphQL data-plane resolver-execution path (the field-resolution component that today only runs APPSYNC_JS code) must evaluate VTL mapping templates: render requestMappingTemplate with the $ctx/$util bindings, dispatch the rendered operation to the resolver's data source (DynamoDB PutItem/GetItem) under its serviceRoleArn, then render responseMappingTemplate into data/errors. Once a mutation resolves, the EventBridge AppSync-target path (endpoint-ARN target + AppSyncParameters.GraphQLOperation + InputTransformer, case-sensitive pattern matching) is what these two checks then grade.

Traces: appsync__dynamodb__events.xsvc-appsync-2-near-miss-events-not-delivered-while-the-pipeline-is-live, appsync__dynamodb__events.xsvc-appsync-2-rule-input-transformer-mutation-writes-the-mapped-item.

## Evidence
Expected (AWS): the signed POST of `mutation PutItem($id: ID!, $kind: String!) { putItem(id: $id, kind: $kind) { id kind } }` answers HTTP 200 with body {"data": {"putItem": {"id": "<id>", "kind": "<kind>"}}} and no "errors" member, and GetItem(ConsistentRead) on the table returns {"id": {"S": "<id>"}, "kind": {"S": "<kind>"}}. Then PutEvents of a matching entry (source "app.ingest", detail-type "ItemArrived", detail.kind in [widget, gadget]) results in the mapped item being written by the rule's AppSync target, while the two near-miss entries (detail.kind "Widget"; detail-type "itemArrived") write nothing and leave the rule's DLQ empty.

Actual (emulator): both checks report exactly `Error: Check timed out after 60.0s`. Neither check ever gets past _warm_resolver()'s bounded wait on a resolving putItem mutation (its own budget is 150 s, so the harness's 60 s cap is what ends them); no item is ever written, so no assertion about EventBridge delivery or near-miss suppression is ever reached. Per-run values in these runs (role names, table names, api ids, event ids) are generated per check and are not part of the requirement.

## Steps to Reproduce
1. iam CreateRole trusting appsync.amazonaws.com with dynamodb:PutItem/GetItem on the table; iam CreateRole trusting events.amazonaws.com with appsync:GraphQL on arn:<p>:appsync:<region>:<account>:apis/<apiId>/types/Mutation/fields/putItem.
2. dynamodb CreateTable (HASH key id:S, PAY_PER_REQUEST), wait ACTIVE.
3. appsync CreateGraphqlApi (authenticationType AWS_IAM); StartSchemaCreation with `schema { query: Query mutation: Mutation } type Item { id: ID! kind: String! } type Query { getItem(id: ID!): Item } type Mutation { putItem(id: ID!, kind: String!): Item }`; wait for SUCCESS.
4. appsync CreateDataSource name=items type=AMAZON_DYNAMODB with dynamodbConfig{tableName, awsRegion} and the appsync serviceRoleArn.
5. appsync CreateResolver for Mutation.putItem with requestMappingTemplate '{"version": "2018-05-29", "operation": "PutItem", "key": {"id": $util.dynamodb.toDynamoDBJson($ctx.args.id)}, "attributeValues": {"kind": $util.dynamodb.toDynamoDBJson($ctx.args.kind)}}' and responseMappingTemplate '$util.toJson($ctx.result)' (and the GetItem variant for Query.getItem).
6. POST the SigV4-signed mutation to the API's GRAPHQL uri. Observed: the mutation never resolves to data.putItem, nothing is written to the table, and the check exhausts its budget.
7. Then events CreateEventBus + PutRule {"source": ["app.ingest"], "detail-type": ["ItemArrived"], "detail": {"kind": ["widget", "gadget"]}} + PutTargets with Arn arn:<p>:appsync:<region>:<account>:endpoints/graphql-api/<host-label>, RoleArn, AppSyncParameters.GraphQLOperation=<the mutation>, InputTransformer{InputPathsMap {id: $.detail.id, kind: $.detail.kind}, InputTemplate '{"id": <id>, "kind": <kind>}'}, RetryPolicy{MaximumRetryAttempts: 0}, DeadLetterConfig; PutEvents one matching and two near-miss entries. Expected: the matching/mapped items are written, the near-miss ids are absent and the DLQ stays empty.
